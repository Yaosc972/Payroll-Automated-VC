# 离职审批漏判修复与验证

## 范围

开发分支 `codex/social-insurance-feedback-20260910`，规则版本 `2026.09.30-01`。本文件随修复提交，尚未部署、未修改生产数据或北森权限。

原连接器只查询已生效的员工任职，没有检查其他审批状态下的离职记录。现按候选 UserID 分批调用 `Employee/GetServiceInfoByIds`，明确指定 `option: "None"`、`approvalStatus: ["Draft", "Approving", "Success", "Refused", "Effective", "Invalid", "Rejected", "Temporary"]`；读取离职业务类型 5。实际调用中，先前的数字 option 0 加空状态列表组合未取到审批中记录，改用上述显式枚举组合后取得两条；未单独归因于其中某个参数。已撤回、草稿、作废等明确无效状态不参与判断。字段缺失或状态无法可靠判断时保守交业务确认，查询失败不能当成无人离职。

真实数据还存在业务类型为空的任职记录：保留为该员工的人工确认事项，不让整批同步失败，也不静默忽略；无效或不匹配的人员标识仍阻断同步。

离职记录不会覆盖新的任职离职信号，也不会让旧快照中已撤回的离职继续自动排除。旧任职最后工作日早于当前入职日时，不阻挡重新入职。JS 同步判断和 Python 快照重算保持一致。

## 已验证

- 修改前观察到回归用例失败：审批中的人员被判为 ready；离职查询失败未阻断。
- Node 连接器测试 39 项通过。
- Python 社保模块测试 183 项通过，含新增端到端测试。
- 端到端：模拟北森 HTTP 响应 → 真实连接器与规则 → 本地 HTTP 连接 → 工作台同步与持久化 → 未确认时拒绝确认/报盘 → 人工排除 → 模板上传 → 下载报盘 ZIP → 打开 Excel 校验。最终仅保留正常入职、重新入职、撤回离职三人，不含被排除的审批中人员。
- 浏览器：待确认 1 人时点击确认被阻止；点击排除后纳入变为 3 人、排除 1 人；确认并下载审核清单，文件中的该人员显示“排除”。测试页面缺少政务字典配置，完整模板上传与报盘验证由上述 HTTP 端到端覆盖。
- 北森真实只读调用：原案例三人工号可匹配，现存离职记录均已生效且标记自愿停保。它们的任职记录创建时间在 9 月 17 日晚，不能冒充原申请时间。另核查本期 203 位候选，返回 4 条已生效离职记录。
- 后续扩展到 272 位候选，找到 2 条真实审批中离职；真实查询返回记录经连接器处理，两人均为待人工确认。将这两条结果放入隔离的本地工作台，经 API 确认和生成报盘均返回 409，跨确认日期重算后仍为待人工确认。此项不是生产环境验收，也不是用真实人员执行报盘提交。

## 未闭环项与发布条件

真实审批中样本的读取及本地拦截已验证。生产尚未部署本次修复，发布后仍需确认生产连接器与工作台版本一致、同步成功且待确认人员不会直接进入报盘。

另外的专用查询 `GetListByBussinessType` 返回 HTTP 401，未采用，未修改授权。

当前接口没有提供已验证的原申请时间，新离职记录使用 `processTimeReliable: false`。但同一自然月入职、1～14 日离职且最后工作日不晚于名单确认日时，明确自愿停保自动排除，明确非自愿停保继续纳入，不再仅因缺少申请时间转人工。15/16 日边界、属性缺失、记录冲突等仍交人工确认；其他依赖申请时点的情况保留原有校验。重新入职前的旧离职仍忽略。

BP 指定购买通过现有人工纳入并填写审核说明处理，未声称从北森自动读取 BP 指示。端到端新增三个模拟人员：早离职自愿停保自动排除、非自愿停保纳入、BP 手工纳入；最终 Excel 包含后两人而不含自动排除者。11 组共享输入分别运行连接器规则与 Python 重算测试，覆盖日期边界、跨月、未来日期、旧任职和冲突。

新旧规则版本、工作台和连接器必须配套发布，不能只发布其中一端。上述新规则未部署生产。
