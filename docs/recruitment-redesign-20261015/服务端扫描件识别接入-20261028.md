# 服务端扫描件识别接入（2026-10-28）

Windows 用户继续用浏览器上传文件，OCR 在后端执行。本次增加 Linux 服务端可用的本地 CPU 识别路径；不要求用户电脑安装 OCR。

## 实现

- 文字型 PDF 继续通过 pypdf 提取原文。
- 扫描 PDF 和图片增加 RapidOCR 3.10.0 / ONNX Runtime CPU 识别。检测、方向分类和文字识别三个模型使用安装包内的明确本地路径，缺模型时报告不可用，不在业务请求中下载模型。
- Mac 后端保留原 Vision 识别；只有未成功读取的页面转入 RapidOCR。识别进程有 180 秒超时，每个进程限制推理线程。
- OCR 输出继续标记需要对照原件核对，不会直接采用审批调整。
- 把识别服务不可用与原件内容未读清分开提示。服务不可用时保留原件，并提示管理员检查服务。
- 文档缓存版本升为 5、附件检查版本升为 4。旧失败扫描缓存、安装依赖前的失败缓存，会在版本或识别能力签名变化后重新识别；已成功读取的长文本不会因此被统一覆盖。没有新增审批采用、金额计算或发薪规则。

本次 OCR 引擎使用跨平台包，但完整应用仍有 Unix 文件锁等既有服务端要求，不声称整个后端已可直接迁到 Windows 原生主机。目标场景是现有后端部署配合 Windows 浏览器。

## 集成与部署步骤

在现有生产 Python 虚拟环境、项目根目录执行：

```bash
python -m pip install -r requirements.txt
python -m bonus_platform.engine.recruitment_ocr --check
```

自检应返回包含以下内容的 JSON：

```json
{"ok": true, "engine": "rapidocr", "models": "bundled", "device": "CPU"}
```

自检会生成临时测试图片并实际识别数字，结束后自动清理。完成集成、自检后，通过现有服务管理方式重启招聘后台，服务名以集成窗口的实际部署为准。

上线后上传一份文字型 PDF、一份扫描 PDF 和一张图片验证。已有识别失败的审批可重新打开核对；仍有旧附件错误时，手动点击“整理资料并核算”或“重新整理已保存资料”刷新。用户无需重传已保留的原件，也无需删除整个 outputs。

本窗口没有执行生产部署。临时验证环境和安装包在验证后清理，生产安装应使用本次依赖文件。

## 验证证据

- 102 个相关 Python 测试通过，覆盖读取、页范围完整性、空白页、失败缓存恢复、审批预览、采用、撤销和原件变更。
- 自检真实执行通过，依赖检查通过。
- 在 Mac ARM64 / Python 3.9.6 上关闭 Vision 分支，实际走跨平台 CPU 引擎识别合成中文 PNG 与扫描 PDF，均识别到 `zt12345` 和周期 `10天`。小样本分别耗时约 1.47 秒和 1.69 秒，不代表真实长审批的性能承诺。
- 直接识别时阻断 Python socket 连接，记录的网络连接尝试为 0。
- 尚未在真实 Linux 生产主机或 Windows 原生后端运行；部署自检是后续上线验证的一部分。
- 证据：`.audit/ocr-portability-20261028/replay-result.json`，复跑脚本和合成样本在同目录。未处理或修改真实活动底稿。
