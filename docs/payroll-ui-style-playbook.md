# 薪酬核算平台 UI 风格复用手册

这份文档用于把 FBU 美洲绩效核算平台前端的设计经验复用到其他薪酬核算项目。新窗口或新项目不能读取历史聊天记录时，直接把本文件作为 UI 设计上下文给 Codex。

## 可直接复制给新窗口的提示词

```text
请参考这套薪酬核算平台 UI 风格做前端：

目标不是做营销页，也不是做大看板，而是做“薪酬专员每天能用的核算工作台”。页面必须低干扰、高密度、强流程感、表格优先。

核心风格：
- 顶部使用 52px 左右的低高度应用栏：左侧放平台 logo + 模块名，中间放 1-2 个主导航按钮，右侧放当前任务主按钮。
- 不要大侧边栏。薪酬核算不是内容管理后台，核心入口收敛到顶部。
- 每个核算活动使用一条横向步骤条：人员校对、考勤工时、薪资数据、绩效数据、核算检查、确认导出。步骤只显示状态，不堆大量数字摘要。
- 上传入口放在对应步骤里，不做全局上传中心，不重复出现同一个上传入口。
- 主内容区域以表格和操作任务为中心。表格、上传材料、名单确认、结果切面是主角，异常/说明只是辅助信息。
- 能自动规则处理的，不要让用户手动配置；能页面内完成的，不跳新页面；能小弹窗解决的，不做大抽屉或长流程。
- 文案必须是用户能懂的话，不使用“阻断项、审计记录、人工确认项、策略上下文”等技术黑话。
- 状态使用轻量标签或状态点：已上传、已解析、按需、必传、已确认、需要处理。不要做大色块。
- 表格固定工号和姓名，数字使用等宽字体。姓名或部门太长时换行或 hover 显示完整值，不要让整行必须横向滚动才看得懂。
- 异常默认降权，只在核算检查或结果说明中出现；不要在每个步骤都放一个巨大异常块。

视觉约束：
- 企业蓝为主色，少量模块色作为强调；状态色只表达状态，不做装饰。
- 背景浅灰，内容白底，细边框，轻阴影。
- 控件圆角 6-8px；卡片 8-12px；不要大圆角气泡堆叠。
- 间距以 4/8px 节奏控制，页面要紧凑但不拥挤。
- 按钮、筛选、输入框高度尽量 32-36px；表格行高约 44-56px。

交互原则：
- 上传后按钮旁边显示状态，不弹大 toast。
- 搜索框必须支持中文输入法 composition，不得输入第一个字母就触发重渲染导致丢字。
- 列表必须支持分页、搜索、批量删除；选择态和删除态要真实可用。
- “查看计算过程”使用小弹窗，内容要解释数字含义和公式，不只展示一串数字。
- 空状态要有轻量插画或结构化提示，但不要占满页面。

请先基于这些规则给出页面结构，再实现 UI。不要照搬 FBU 文案，业务字段按当前项目调整。
```

## 设计判断

薪酬核算页面的重点是“把一轮月度核算做完”，不是展示系统能力。用户关心的是：

- 现在核算到哪一步。
- 哪些材料已经上传、解析是否成功。
- 还差什么才能继续。
- 核算结果人数、金额和差异是否可信。
- 某个员工为什么是这个结果。
- 最后能否按线下结果表样式导出。

因此页面不应该把空间花在大标题、大异常块、大说明文案和重复入口上。

## 推荐页面骨架

### 1. 顶部应用栏

用途：提供平台归属、模块切换和主操作。

建议结构：

- 左侧：Sigma logo + 模块名。
- 中间：模块主入口，例如“核算工作台”“活动列表”。
- 右侧：新建月度活动、返回、导出等当前页主操作。

不要：

- 不要再放一个大侧边栏。
- 不要把模块名做成下划线链接。
- 不要在顶部塞过多统计数字。

### 2. 活动页头

用途：告诉用户当前处理的是哪个月份、哪个活动、当前步骤。

建议结构：

- 标题：`2026-04 FBU美洲绩效核算` 这种明确业务名。
- 副信息：活动 ID、当前步骤。
- 右侧只放 1-2 个动作，例如“开始核算”“返回”。

### 3. 横向步骤条

用途：承载全流程，不靠左侧多页导航。

推荐步骤：

1. 人员校对
2. 考勤工时
3. 薪资数据
4. 绩效数据
5. 核算检查
6. 确认导出

规则：

- 当前步骤用蓝色锚点图标。
- 已完成步骤用绿色对勾。
- 未开始步骤灰色。
- 步骤下只显示状态：已完成、需要处理、未开始。
- 不要在步骤条下放大数字摘要。

### 4. 步骤内容区

每个步骤只展示当前步骤必须处理的东西。

推荐组合：

- 上传文件卡片：放在对应步骤内。
- 名单确认：与上传区并排或紧邻。
- 表格预览：展示本步骤核心数据。
- 需要处理：只列真正影响继续核算的事项。

不要：

- 不要在一个全局上传区里放所有入口。
- 不要多个位置都能上传同一份文件。
- 不要把“说明”“异常”“审计”做成主视觉。

### 5. 结果页

结果页应该像线下最终表，而不是普通后台列表。

推荐：

- 顶部放结果摘要：人数、奖金总额、分组人数、分组金额。
- 用切面切换：汇总表、仓库管理人员、非仓人员、区长。
- 表头学习线下 Excel：分组表头、深蓝表头、关键字段高亮。
- 96 工时制、调薪、区长等非标准人员，在姓名旁放轻标签。
- “计算过程”列用小按钮打开弹窗，解释公式、来源和每个数字含义。

不要：

- 不要只放一张大表。
- 不要把时薪等中间敏感字段默认暴露在最终结果。
- 不要让职位、部门等字段显示 HTML 字符串。

## 组件规则

### 上传卡片

上传卡片是材料入口，不是大卡片展示区。

推荐字段：

- 材料名：考勤日报、上月考勤、薪资档案、绩效报表、补充假勤。
- 标签：必传、按需、96工时制员工。
- 提示小字：上传 OEHR 当月考勤日报表。
- 文件名和状态：已上传、已解析、解析中。
- 按钮：上传、重新上传、选择文件。

布局：

- 可两列并排。
- 高度控制在 92-130px。
- 上传进度条细而短。
- 上传状态放按钮旁边或文件名旁边，不弹大提示。

### 表格

表格是核算系统的主界面。

推荐：

- 表头浅蓝灰底，细分割线。
- 固定工号和姓名。
- 金额、小时、系数使用等宽数字。
- 长姓名、长部门支持换行或 hover 完整提示。
- 页面放不下时优先减少列宽和换行，而不是让用户必须横向滚动。
- 所有表格必须分页。
- 搜索框放表格右上角。

不要：

- 不要大复选框。
- 不要厚重状态色块。
- 不要把筛选做成大浮层，除非字段太多。

### 状态

推荐状态文案：

- 已上传
- 已解析
- 解析中
- 按需
- 必传
- 已确认
- 需要处理
- 已排除
- 确认计入

避免：

- 阻断项
- 审计记录
- 人工确认项
- 策略命中
- 规则上下文
- 物理拆行

### 说明与计算过程

说明不是主界面正文。

推荐：

- 简短说明条只放一行。
- “查看说明”可折叠，但不要抢主视线。
- “计算过程”必须是小弹窗，内容按字段解释：
  - 绩效基数：来源和公式。
  - 绩效比例：来自薪资或调薪。
  - 绩效系数：来自绩效报表或页面补录。
  - 最终奖金：基数 × 比例 × 系数。

## 流程复用模板

其他薪酬项目可以按这个结构套：

```text
首页 / 活动列表
  - 顶部应用栏
  - 活动统计卡片
  - 活动列表表格：月份、阶段、范围、检查、金额、创建时间、操作
  - 支持分页、搜索、批量删除

月度活动
  - 活动页头
  - 横向步骤条
  - 当前步骤内容
  - 本步骤完成状态
  - 本步骤核心表格

结果导出
  - 结果摘要
  - 多切面结果表
  - 计算过程弹窗
  - 导出按钮
```

## 反例清单

看到这些情况应优先修：

- 顶部大横幅 + 大异常块 + 大卡片堆叠，表格反而靠下。
- 同一个上传入口出现在多个地方。
- 新建活动后跳到后面步骤，而不是从第一步开始。
- “上传中 / 解析中”没有真实状态或卡住没有恢复。
- 搜索框中文输入丢字。
- 批量删除、单个删除按钮看起来能点但无效。
- 空表格还显示分页和巨大空框。
- 状态 toast 连续堆叠。
- 表格列里出现 `<span class=...>` 这种 HTML 字符串。
- 最终结果没有汇总表，也没有按业务分组切面。

## 给 Codex 的执行要求

在其他项目使用这套风格时，先做这几步：

1. 读项目现有 `DESIGN.md` 或样式文件。
2. 找当前业务的线下最终表或用户真实操作流程。
3. 先画页面结构，不急着写 CSS。
4. 把入口收敛到步骤内。
5. 先保证关键交互可用：上传、搜索、分页、删除、导出、查看计算过程。
6. 用浏览器端到端测试，不只跑语法检查。

验收标准：

- 用户第一眼能知道当前核算月份、当前步骤、还差什么。
- 一份材料只有一个上传入口。
- 表格是主内容，说明和异常不抢主视觉。
- 全流程不依赖侧边栏层层跳转。
- 页面没有技术黑话。
- 所有按钮和搜索都真实可用。
