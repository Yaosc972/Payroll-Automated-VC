# FBU核算活动流程改造设计

## 背景

当前 FBU 美洲绩效核算页面把月度活动、基础数据、异常队列、考勤、薪资、绩效和结果拆成多个左侧入口；工作台内又堆叠数据源卡片、待处理卡片、结果表和说明卡片。对薪酬专员来说，这不像一次核算活动，更像多个功能页拼在一起。

这次改造目标是参考发薪活动类产品，把 FBU 核算收敛成一个按步骤推进的活动页。用户只需要按顺序完成每一步，材料入口只出现在该步骤，真正需要处理的事项只在当前步骤出现。

## 目标

1. 把 FBU 活动内流程改成 6 步：人员核对、考勤工时、薪资数据、绩效数据、核算检查、确认导出。
2. 左侧侧边栏不再承载 FBU 业务流程入口，只保留平台级图标导航。
3. 同一材料全流程只有一个上传入口，入口放在对应步骤。
4. 只把缺关键数据、无法继续核算、必须用户处理的事项显示为“需要处理”。
5. 页面文案使用用户能理解的动作语言，不出现内部技术词。
6. 表格优先，减少卡片、气泡、大段说明和重复按钮。

## 不在范围

1. 不改现有奖金计算公式。
2. 不改员工 ID、白夜班拆分、补充假勤、转正调薪等业务规则含义。
3. 不重做后端数据模型，除非实现时发现前端无法表达步骤状态。
4. 不引入 React、shadcn、Tailwind 或新的前端依赖。现有页面是 HTML/CSS/JS，上传体验只借鉴 timeline upload 的交互模式。

## 页面层级

页面只有两层：

1. 活动列表
2. 活动详情

活动列表负责创建、进入、查看历史活动。它不放在左侧侧边栏，也不是活动内流程步骤。

活动详情顶部显示当前活动，例如：

`2026-04 FBU美洲绩效核算`

标题旁保留 `返回活动列表`。右侧最多保留当前步骤的主动作和一个必要辅助动作。不要在顶部堆放花名册、导出检查结果、执行核算、新建活动等多个入口。

## 活动步骤

活动详情主体使用横向步骤条：

`1 人员核对 -> 2 考勤工时 -> 3 薪资数据 -> 4 绩效数据 -> 5 核算检查 -> 6 确认导出`

步骤条规则：

1. 步骤名清晰展示。
2. 摘要数字用小字号，不做大 KPI。
3. 状态只用用户语言：未开始、未完成、已完成、需要处理。
4. 顶部步骤条不展示全局待处理列表。
5. 点击步骤切换当前工作区，不依赖左侧侧边栏。

## 上传入口规则

上传入口按步骤唯一归属。同一种材料不能同时出现在顶部、卡片、弹窗、侧栏或多个步骤。

上传交互采用紧凑材料行，不做大上传区，不做卡片墙。

未上传：

`考勤日报  必传  上传OEHR当月考勤日报表  [上传]`

上传中：

`考勤日报  正在上传  原始考勤日报表.xlsx  72%  [取消]`

已上传：

`考勤日报  已上传  原始考勤日报表.xlsx  [重新上传]`

上传失败：

`考勤日报  上传失败  文件格式不对  [重新上传]`

上传成功后只显示文件名，不显示上传时间、文件大小、解析行数、结果文件。必要说明放到当前步骤的 `查看说明`。

长期稳定的小名单不做上传材料，改为页面内维护。用户每月可以直接确认沿用，也可以按需修改。

## 步骤设计

### 1. 人员核对

目的：确认本月要算奖金的人是谁。

上传入口：

| 材料 | 标签 | 小字 |
| --- | --- | --- |
| 花名册 | 必传 | 上传人员基础资料 |

内容：

1. 人员统计：本月人员、新增、离职仍需发放、未匹配。
2. 人员表：工号、姓名、部门、岗位、状态、是否参与本月核算。
3. 需要处理：花名册缺失、员工重复、员工身份无法确认。

不放考勤、薪资、绩效上传入口。

### 2. 考勤工时

目的：确认用于计算奖金基数的工时。

上传入口：

| 材料 | 标签 | 小字 |
| --- | --- | --- |
| 考勤日报 | 必传 | 上传OEHR当月考勤日报表 |
| 上月考勤 | 96工时制员工 | 上传OEHR上月考勤日报表 |
| 补充假勤 | 必传 | 上传线下sickpay与年假补充数据 |

规则：

1. 上月考勤只在系统判断存在 96 工时制跨月需要时显示。
2. 补充假勤是必传材料，未上传时本步骤不能完成。
3. 补充假勤只展示需要用户确认的行；已自动判断的内容不占页面。

页面内维护：

| 名称 | 默认状态 | 操作 |
| --- | --- | --- |
| 96工时制员工 | 初始化当前已确认的 4 名员工 | 确认名单 / 管理 |

维护规则：

1. 96工时制员工不做上传。
2. 每月默认带出当前已确认的 4 名员工。
3. 用户可以直接点击 `确认名单` 沿用本月名单。
4. 用户可以在当前步骤内新增、停用、删除员工。
5. 系统按这份名单判断是否需要上月考勤。
6. 白班拆分必须精确匹配 `原工号-1`，不允许模糊匹配。

内容：

1. 工时表：工号、姓名、普通工时、计入病假/年假小时、96 工时制拆分、需要处理。
2. 需要处理：缺考勤、补充假勤未确认、96 工时制名单未确认、96 工时制跨月材料缺失。

### 3. 薪资数据

目的：确认奖金计算所需的薪资数据。

上传入口：

| 材料 | 标签 | 小字 |
| --- | --- | --- |
| 薪资档案 | 必传 | 上传OEHR最新薪资档案（含离职） |
| 当月转正/调薪表 | 按需 | 上传OEHR转正调薪流程 |

页面内维护：

| 名称 | 默认状态 | 操作 |
| --- | --- | --- |
| 固定基数人员 | 初始化当前已确认名单 | 确认名单 / 管理 |

维护规则：

1. 固定基数人员不做上传。
2. 每月默认带出当前已确认名单。
3. 用户可以直接点击 `确认名单` 沿用本月名单。
4. 用户可以在当前步骤内新增、停用、删除员工，也可以修改固定基数金额。
5. 启用固定基数的员工，本月按固定基数参与奖金计算。

内容：

1. 薪资表：工号、姓名、时薪、绩效比例、转正/调薪状态、固定基数状态、是否可计算。
2. 需要处理：缺薪资、0 时薪、绩效比例缺失、转正/调薪无法自动拆分、固定基数名单未确认。

不放绩效得分补录，不放考勤明细。

### 4. 绩效数据

目的：确认绩效得分和绩效系数。

上传入口：

| 材料 | 标签 | 小字 |
| --- | --- | --- |
| 绩效报表 | 必传 | 上传OEHR当月绩效报表 |

页面内填写：

1. 离职人员绩效，不做上传。

内容：

1. 绩效表：工号、姓名、得分、等级、系数、来源。
2. 需要处理：缺绩效且不能自动使用默认系数、离职人员需要补充得分。

### 5. 核算检查

目的：核算前确认当前活动是否可以继续。

内容：

1. 主按钮：开始核算或重新核算。
2. 只展示必须处理的问题：缺关键数据、无法继续核算、必须用户确认。
3. 预览：可计算人数、暂不可计算人数、预计奖金总额。
4. 当前步骤没有问题时，显示短句：本步骤已完成。

不展示完整问题清单，不展示上千条普通提示，不使用严重/提醒/信息这种技术分级。

### 6. 确认导出

目的：查看最终结果并导出。

内容：

1. 最终结果表：工号、姓名、部门、岗位、绩效得分、绩效基数、绩效比例、绩效系数、最终奖金。
2. 默认按最终合并结果展示，白班/夜班拆分只在行内展开。
3. 行内提供 `查看说明`，展示计算过程，不用弹窗。
4. 导出按钮只在此步骤出现。

不放上传入口，不放非最终数据源卡片。

## 表格规则

1. 表格固定列只固定工号和姓名。
2. 数字列右对齐，金额和小时使用等宽数字。
3. 默认只展示当前步骤需要看的字段。
4. 需要更多说明时用行内展开，不弹窗。
5. 不把普通提示标成需要处理。

## 人员小标签

特殊人员在姓名旁展示小标签，帮助用户一眼识别这个人的计算方式和普通员工不同。小标签不是需要处理，也不使用红色警示样式。

展示位置：

1. 各步骤表格的姓名列。
2. 确认导出步骤的最终结果表。
3. 行内展开的计算说明里可以重复展示，但不要在页面其他位置额外堆列表。

标签示例：

| 标签 | 出现条件 |
| --- | --- |
| 区长 | 员工使用区长或类似管理岗奖金规则 |
| 96工时制 | 员工在 96 工时制名单中且本月参与计算 |
| 固定基数 | 员工本月启用固定基数 |
| 存在调薪 | 员工本月存在转正或调薪拆分 |
| 离职发放 | 员工已离职但本月仍需发放绩效奖金 |

样式规则：

1. 小标签紧贴姓名右侧，字号小于正文。
2. 默认用灰蓝或浅蓝样式，不使用大面积色块。
3. 一个员工最多默认展示 3 个标签；更多标签收进 `+N`。
4. 标签不替代表格字段。需要看金额、工时、系数时仍看对应列或行内说明。

## “需要处理”规则

页面只把以下情况显示为“需要处理”：

1. 缺少必传材料。
2. 员工无法匹配到关键数据。
3. 数据为 0 或为空且会导致无法计算。
4. 系统已给建议但必须用户确认。
5. 上传失败或文件格式不符合要求。

以下内容不进入“需要处理”：

1. 已自动完成的普通处理。
2. 可追溯但不影响继续核算的说明。
3. 信息级提示。
4. 已经处理完成的历史记录。

每个步骤内只显示当前步骤的需要处理事项，不做顶部全局待处理区。

## 查看说明

每个步骤右上角有一个 `查看说明`，默认收起。

用途：

1. 解释当前步骤已自动处理的内容。
2. 帮用户理解为什么某些数据已被计入、排除或拆分。
3. 只用短句列表，不放长段规则。

示例：

考勤工时：

1. 普通病假、年假已按申请时间计入本月。
2. 离职年假默认不计入。
3. 96工时制员工已按上月和本月考勤合并计算。

薪资数据：

1. 当月转正/调薪已按生效日期拆分。
2. 未发生转正/调薪的员工按薪资档案直接计算。

绩效数据：

1. 有绩效报表的员工按报表得分计算。
2. 离职员工可在本页补充绩效得分。

## 文案规则

页面文案必须使用用户能理解的词。

禁止出现在页面上的词：

1. 诊断
2. 阻断项
3. 审计记录
4. 人工确认项
5. 口径
6. 链路
7. 上下文
8. 规则命中
9. 来源映射
10. 异常记录

推荐替换：

| 不使用 | 使用 |
| --- | --- |
| 异常队列 | 需要处理 |
| 诊断详情 | 检查结果 |
| 审计记录 | 查看说明 |
| 阻断项 | 需要处理 |
| 人工确认项 | 请确认 |
| 规则命中 | 已自动处理 |
| 计算链路 | 计算说明 |

## 视觉规则

1. 参考发薪活动类页面：白底、轻边框、低阴影、表格为主。
2. 控件圆角控制在 4px 到 8px。
3. 不做大气泡、大圆角、大色块、卡片套卡片。
4. 必传、已上传、需要处理等状态使用小标签。
5. 步骤摘要小字号展示，不做大数字。
6. 页面主动作数量受控：当前步骤最多一个主按钮。

## 验收标准

1. 左侧不再出现 FBU 业务流程入口。
2. 活动详情按 6 步展示，点击步骤切换工作区。
3. 每类材料只有一个上传入口，且入口在对应步骤。
4. 上传行紧凑展示，上传成功后只显示文件名。
5. 补充假勤是必传材料。
6. 96工时制员工不上传，考勤工时步骤内初始化当前已确认的 4 名员工，并支持确认或修改。
7. 上月考勤只在 96 工时制跨月需要时展示。
8. 固定基数人员不上传，薪资数据步骤内初始化当前已确认名单，并支持确认或修改。
9. 顶部不展示全局待处理列表。
10. 当前步骤只展示本步骤需要处理的事项。
11. 页面不出现禁用词列表中的技术黑话。
12. 表格固定列只固定工号和姓名。
13. 姓名旁展示特殊人员小标签，例如区长、96工时制、固定基数、存在调薪、离职发放。
14. 小标签不算需要处理，不使用红色警示样式。
15. 最终导出只在确认导出步骤出现。
16. 最终结果默认合并白夜班，拆分明细通过行内展开查看。

## 实施边界

本设计先改前端信息架构和展示行为。现有接口可以继续使用；如实现时发现需要补充步骤状态字段，应新增轻量字段并保持原有数据兼容。

实现应优先改 `bonus_platform/static/fbu-performance.html` 和 `bonus_platform/static/fbu-performance.js`，不要把本次 UI 改造扩散到海外劳务或其他模块。
